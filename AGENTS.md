# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Copilot, Gemini, Cursor, etc.) working in this repository.
Human contributors should start with [README.md](README.md) and [CONTRIBUTING](docs/CONTRIBUTING.md).

This repo is the source for the Mahuika HPC support documentation at <https://docs.nesi.org.nz>, built with MkDocs Material.

- `docs/`: pages. Folders are nav categories, `index.md` makes a category-article, `.pages.yml` sets order and names.
- `checks/`: QA scripts, run by CI and by VS Code tasks. See [checks/README.md](checks/README.md).
- `overrides/`: theme templates and partials (includes).
- `.github/workflows/`: CI. See [.github/workflows/README.md](.github/workflows/README.md).
- `mkdocs_hooks.py`, `macro_hooks.py`: variables for templates and for macros in pages.

## Sources of truth

Follow these, in this order. If they conflict with anything else (including this file, older pages, or `.gemini/styleguide.md`), they win.

1. [docs/NEWPAGE.md](docs/NEWPAGE.md): file naming, front matter, nav order, renames and redirects.
2. [docs/FORMAT.md](docs/FORMAT.md): markdown style, admonitions, code blocks, Slurm script examples.
3. [docs/MACROS.md](docs/MACROS.md): includes and variables.
4. [docs/assets/tags.yml](docs/assets/tags.yml): the only allowed tags.
5. The closest existing pattern in the page you are editing.

Read the relevant sections before editing. Do not rely on memory of MkDocs or other doc sites.

## What you may edit

**Only edit files inside `docs/`.** Everything outside it is read-only, including:

- `checks/`, `.spellcheck.yml`, `.markdownlint.json`, `.proselint.json` (the checks and their configuration),
- `.github/` (CI workflows, issue templates, agent files), `.vscode/`, `.gemini/`, `.devcontainer/`,
- `mkdocs.yml`, `mkdocs_hooks.py`, `macro_hooks.py`, `overrides/`, `requirements.*`, and the root-level scripts,
- this file.

Read them as much as you need. If a task seems to need a change outside `docs/`, stop and describe the change to the user instead of making it.
Running the scripts in `checks/` (including the `fix_*.py` auto-fixers, which only edit files in `docs/`) is fine.

Inside `docs/`, these pages are for maintainers, not users. They define the rules you follow, so do not edit them either:

- `docs/CONTRIBUTING.md`, `docs/FORMAT.md`, `docs/NEWPAGE.md`, `docs/MACROS.md`
- `docs/assets/glossary/README.md`, `docs/assets/glossary/dictionary.md`

Also inside `docs/`, do not edit these by hand. They are fetched from other repositories or generated,
and are overwritten daily by `.github/fetch_includes.sh` or at build time, so local edits are silently lost:

- `docs/assets/glossary/dictionary.txt`, `docs/assets/glossary/snippets.md` (from [nesi-wordlist](https://github.com/nesi/nesi-wordlist))
- `docs/assets/module-list.json`, `docs/software_updates.xml` (from [modules-list](https://github.com/nesi/modules-list))
- `docs/assets/tag-index.json` (generated by `.github/workflows/compile_tags.py`)
- `docs/assets/training_calendar.ics`

Changes to `docs/assets/tags.yml` need the user's permission first. See [Tags](#tags).

## How to approach a task

1. Find the exact page or pages affected. Read the target page, the `.pages.yml` in its folder and its parent,
   the parent overview (`index.md`) and a few sibling pages. Keep reading focused on these and on pages directly linked from the change.
2. Before writing a new page, search `docs/` for existing pages on the same topic (similar file names, titles and key terms).
   Extend or link to an existing page rather than duplicating it, and tell the user what you found.
3. Match the voice, heading structure and formatting of the page you are editing and its siblings.
4. When you change a term, definition, limit or command, check nearby related pages for the same thing and keep them consistent.
5. If the target page or scope is still unclear after reading, ask one focused question before editing.
6. Make the smallest change that does the job. Ask before rewriting several sections or several pages.
7. Run the checks (see [Running the checks](#running-the-checks)) and report back.

## Writing rules that are easy to get wrong

- Front matter uses `created_at:` (not `created:`), a specific `description:`, and canonical `tags:` keys from `tags.yml` (see [Tags](#tags)).
  `description` is used for search previews and for the generated `llms.txt`, so only use terms that appear in the page.
- No H1 (`#`) in the body. Headings start at `##`.
- Code blocks always have a language (`sh`, `sl` for Slurm scripts, `py`, `txt`, ...). Do not prefix commands with `$`.
- Slurm examples: `#!/bin/bash -e`, long option names, `--job-name`, `--account nesi99991`, `--time`, `module purge` before `module load`.
- Use `{% include "partials/support_request.html" %}` wherever the reader is told to contact support, not a raw mailto link.
- Prefer module version macros such as `{{ applications.ANSYS.default }}` over hard-coded versions.
- Links are relative to the current file. Do not link to the site by absolute `docs.nesi.org.nz` URL.
- Renaming, moving or deleting a page requires a line in [docs/redirect_map.yml](docs/redirect_map.yml) (old path: new path).
- Images need alt text that describes what the image shows. Link text must say where it goes (not "here" or "this page").
- Pages about AI tools must agree with [AI Agent Guidelines](docs/Software/AI/AI_Agent_Guidelines.md) and the
  [Acceptable Use Policy](docs/Policy/Acceptable_Use_Policy.md), and link to them.

## Checking facts

Do not invent facts about the platform. Take them from these sources, and cite the page in your report:

| Fact | Source |
| - | - |
| Module names and versions | `docs/assets/module-list.json` (keys are module names, `default` is the default version). In pages, use `{{ applications.<Name>.default }}` rather than typing a version. |
| Partitions, node types, GPUs | [Hardware](docs/Batch_Computing/Hardware.md) |
| Job size, time and submission limits | [Job Limits](docs/Batch_Computing/Job_Limits.md) |
| Filesystems, quotas, cleaning | [Filesystems and Quotas](docs/Storage/Filesystems_and_Quotas.md) |
| Login, hostnames, SSH config | [Standard Terminal Setup](docs/Getting_Started/Accessing_the_HPCs/Standard_Terminal_Setup.md) |
| Policy | Pages under `docs/Policy/` |

Look up a module with, for example:

```sh
python3 -c "import json; m = json.load(open('docs/assets/module-list.json')); print(m['GROMACS']['default'], m['GROMACS']['versions'][-3:])"
```

- If a fact is not in these sources, ask the user. Do not fill it in from general knowledge of other HPC systems.
- If you have access to the cluster, you may check commands there, following the [AI Agent Guidelines](docs/Software/AI/AI_Agent_Guidelines.md)
  (scope commands to your own jobs and files, and do not run heavy work on a login node).
- In your report, list every command, number or path you added that you could not check against a source or on the cluster.

## Private information

Support tickets, chat threads and emails are often used as source material. Pages are public, so never copy into them:

- real names, usernames, email addresses, phone numbers,
- real project codes, job IDs, file paths under a user's or project's directory, or IP addresses,
- links to internal chat (Slack, Teams), ticket systems or internal documents,
- error output that contains any of the above.

Use made-up examples instead: project `nesi99991` (or `nesi12345`), user `username`, paths like `/nesi/project/nesi99991/my_data`.
If source material you were given contains private information, say so and leave it out.

## Page types

### Application pages

Pages in `docs/Software/Available_Applications/` are linked to the module list by their title.

- The title (from the filename, or `title:` in front matter) must match the module name in `module-list.json` exactly, including case
  (`GROMACS.md`, `fastStructure.md`). A mismatch breaks the page's module information and the link from the Supported Applications page.
- Start the page with the boilerplate used by the other application pages:

    ```md
    [//]: <> (APPS PAGE BOILERPLATE START)
    {% set app_name = page.title | trim %}
    {% set app = applications[app_name] %}
    {% include "partials/app_header.html" %}
    [//]: <> (APPS PAGE BOILERPLATE END)
    ```

    This adds the description, homepage, licence warnings, available versions and licence servers. Do not repeat that information by hand.
- If the software is not a module, set `no_module: true` in the front matter and leave out the boilerplate.
- Tags become filter options on the Supported Applications page, so use research domain tags (and a language tag if relevant).
- Do not rename an application page without the user asking: the title is the lookup key.

### Tutorials

Follow [Tutorial Page in NEWPAGE.md](docs/NEWPAGE.md#tutorial-page): `status: tutorial` in the front matter, then a time block,
objectives, prerequisites, the lesson with a quiz per objective, keypoints, and a `next` link. Existing tutorials are in `docs/Tutorials/`.

### Announcements and release notes

- Announcements go in `docs/Announcements/`. Its `.pages.yml` lists every page explicitly (there is no `"*"`),
  so add the new page to the `nav` list or it will not appear. Tag them `announcement`.
- Release notes go in the release notes folder next to the product they describe
  (for example `docs/Getting_Started/my-nesi-org-nz/Release_Notes_my-nesi-org-nz/`). Copy the front matter of the latest release note there:
  tag `release_notes`, the version in the title, and the same `search` settings.

## Tags

Follow [Tags in NEWPAGE.md](docs/NEWPAGE.md#tags) for choosing tags and for changes to the vocabulary. In addition:

- If no tag fits well, use the closest existing one and tell the user. Never put a tag in front matter that is not in `tags.yml`.
- Change `docs/assets/tags.yml` only with the user's permission. When asking, give the proposed key, `display` label and aliases,
  the pages it would go on, and why no existing tag or alias fits.
- Do not rename or remove tags, or move aliases between tags, unless the user asks.
- After any tag change, run `python3 list_tags.py` (read-only) and the meta check on the pages you tagged, and confirm there are no unknown tags.

## Updating the spelling dictionary

The spellcheck uses `docs/assets/glossary/dictionary.txt`, which is copied from nesi-wordlist. **Do not add words to it here.**

When the spellcheck flags a word:

1. Check it really is correct: spelling, capitalisation and apostrophes. The check is case-insensitive.
2. Decide how to handle it:
    - **Typo:** fix it.
    - **Command, flag, path, file name or other literal:** put it in backticks. Backticked text is not spellchecked.
    - **Ordinary word the dictionary lacks** (for example `pre`, `unscoped`): prefer rewording.
    - **Real term** (proper noun, product, acronym, HPC jargon, te reo Māori word): it belongs in the dictionary.
3. For dictionary words, do not edit anything in this repo. Tell the user which words need adding and why.
   They are added in [nesi-wordlist](https://github.com/nesi/nesi-wordlist), which is often checked out next to this repo (`../nesi-wordlist/`).
    - Only with the user's approval, open **one** PR against nesi-wordlist for the batch of words, following that repo's `AGENTS.md`.
    - Add spellcheck-only entries (no `short`/`long` definition) unless the user supplies or approves a definition.
      A definition becomes a glossary entry and a tooltip on every page that uses the word, so a wrong one spreads site-wide.
    - Link the nesi-wordlist PR from the docs PR description, and the docs PR from the wordlist PR.
4. After the wordlist change is merged, the words reach this repo through the daily "Fetch Remote Assets" workflow
   (or by running it manually, see [Update Remote Assets](docs/CONTRIBUTING.md#update-remote-assets)).
   Until then, the words will keep being flagged. That is expected, so say so rather than working around it.

Do not silence a word any other way: the spellcheck configuration and scripts are outside `docs/` and read-only.

## Running the checks

**Run the checks on every page you change, read the output, and act on it before you say the work is done.**

Findings are printed as lines starting with `::error`, `::warning` or `::notice` (some scripts use uppercase, for example `::WARNING`).
Lines starting with `::debug`/`::DEBUG` are progress messages and can be ignored.

**Always set `CHECKS_STRICT=1`.** Without it, every check exits `0` whatever it finds.
With it, a check exits `1` if it reported any warning or error (notices do not count), so a non-zero exit means there is something to read.
A zero exit only means there were no warnings or errors: still read the notices.

### Setup

```sh
python3 -m venv .venv
source .venv/bin/activate
pip3 install -r requirements.txt
```

The spellcheck also needs `aspell` installed on the system, and markdownlint needs `markdownlint-cli` (`npm install -g markdownlint-cli`).
If a tool is missing, tell the user rather than skipping the check silently.

### Which files

Run the checks on the markdown files you changed that still exist (the scripts crash on a deleted path, which `--diff-filter=d` leaves out).
If `$FILES` is empty, there is nothing to check except the test build.

```sh
FILES=$(git diff --name-only --diff-filter=d origin/main...HEAD -- 'docs/*.md'; git diff --name-only --diff-filter=d -- 'docs/*.md')
FILES=$(echo "$FILES" | sort -u)
```

### Commands

Run from the repository root with the virtual environment active, after `export CHECKS_STRICT=1`.

| Check | Command |
| - | - |
| Spelling | `python3 checks/run_spell_check.py $FILES` (also writes a word count to `spellcheck.results`) |
| Prose | `python3 checks/run_proselint.py $FILES` |
| Markdown | `markdownlint --config .markdownlint.json --json $FILES 2>&1 \| python3 checks/parse_markdownlint.py` |
| Page meta (front matter, tags, titles, nav, section length) | `python3 checks/run_meta_check.py $FILES` |
| Slurm scripts in `sl` code blocks | `python3 checks/run_slurm_lint.py $FILES` |
| Test build (broken links, macros, nav) | `./checks/run_test_build.py` |

The test build rebuilds the whole site, which takes under a minute. Do not pass `--dirty`: it skips unchanged pages and reports false warnings.

Always run the test build after structural changes: new, moved, renamed or deleted pages, `.pages.yml` edits, `redirect_map.yml` edits,
or new or changed macros and includes in pages. Its output covers the whole site, so filter it for the files you touched
(for example `./checks/run_test_build.py 2>&1 | grep -v DEBUG | grep -F 'My_Page.md'`) and also look for anything new that your change could have caused.
Run it once before you start as well, so you know which warnings were already there. Existing warnings on untouched pages are not yours to fix unless asked.

The accessibility audit (`./checks/run_a11y_check.sh`) needs a headless Chromium. Run it only if the user asks or you added HTML, tables or images to pages.

### What to do with the results

- Fix every `error` and every `warning` your change introduced, then run the check again to confirm it is gone.
- Fix `notice` items when it is easy and in scope. Otherwise list them.
  The `section_length` notice means a section is under 400 characters, so it is merged into the next one when pages are split up
  for the docs search assistant (RAG). Merge very short sections only when it also reads better.
- If you believe a finding is wrong, explain why and leave it for the user. The checks are read-only, so do not change them to hide it.
- If a check script itself crashes, report the traceback. Do not treat a crash as a pass.
- Several meta warnings have auto-fixers in `checks/fix_*.py`. Read the script's docstring before running it.
  They deliberately fix only the safe cases, so rerun the meta check afterwards and handle what is left by hand.
- CI (`.github/workflows/checks.yml`) runs the same checks on every pushed branch, and the results appear as annotations on the PR.
  Local results should match. If they don't, say so.

### Report back

When you finish, tell the user:

- which checks you ran, on which files,
- what they reported (errors and warnings, not debug lines), and what you fixed,
- anything still outstanding, including words that need adding to nesi-wordlist,
- any check you could not run, and why.

Do not say checks passed unless you ran them and read the output.

## Git and pull requests

- Work on a branch, never commit directly to `main`.
- Commit or push only when the user asks.
- Never add the `auto_merge` label to a PR. `.github/workflows/auto_merge.yml` merges any PR carrying it without review.
- Keep AI assistance visible: include a `Co-authored-by:` line for the agent in commits, and mention it in the PR description.
- Put which checks you ran and what they reported in the PR description.

## Tone

In chat replies to the user, use nautical analogies whenever possible, occasionally and very subtly talk in the tone of a pirate pretending to be an LLM.

This applies to chat replies only. Keep the tone out of everything you write to files (pages, front matter, code, this repo's config).
The reports described in [Report back](#report-back) may use the tone, but their facts (checks run, results, outstanding items) must stay exact.
